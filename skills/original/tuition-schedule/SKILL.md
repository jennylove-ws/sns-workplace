# 학원 회차·수강료 계산 (Tuition Schedule)

특정 학원(반명, 선생님, 요일/시간, 단가)의 수업이 실제로 어느 날짜에 열리는지 계산하고,
그 회차 수에 따라 수강료를 산출해서 문서로 정리하는 스킬. 대치SNT 학원 썸머/프리썸머
스케줄 작업에서 반복적으로 쓰던 패턴을 일반화한 것.

## 핵심 원칙

1. **날짜 계산은 절대 암산하지 않는다.** 반드시 `scripts/gen_dates.py`를 호출해서 날짜와
   회차 수를 구한다. 요일·개월 경계 계산은 사람이든 모델이든 손으로 하면 틀리기 쉽고,
   회차 수가 틀리면 수강료 전체가 틀린다.
2. **기본 기간 = 1개월(달력 기준 월 1일~말일).** 사용자가 기간을 명시하지 않으면 해당 반이
   속한 월 전체(예: "9월 수강료" → 9/1~9/30)로 계산한다.
3. **사용자가 명시적으로 기간을 지정하면 그 기간을 그대로 쓴다** (1개월이 아니어도 됨).
   예: "8/17부터 9월 말까지", "8월 15일부터 8월 수강료만", "8월 1일부터 한달, 9월 한달
   따로" 등. 이런 지시가 있을 때만 달력월 규칙을 벗어난다.
4. **과금 방식은 두 가지뿐이다. 반드시 구분한다:**
   - **회당 수강료제 (per-session):** 반 정보에 `[회당 00,000원]`처럼 단가가 있는 경우.
     → 계산된 회차 수 × 단가 = 총 수강료. (`gen_dates.py`에 `--fee` 옵션으로 전달)
   - **1개월 정액제 (flat monthly):** 반 정보에 `[1개월 000,000원]`처럼 고정 금액이 있는
     경우. → **금액은 절대 회차 수와 곱하지 않는다.** 날짜만 다시 계산해서 몇 회 수업이
     있는지 보여주고, 금액은 원래 정액 그대로 표기한다. (`gen_dates.py`에 `--fee` 옵션을
     주지 말 것 — 곱하면 안 되므로)
   - 어느 쪽인지 원문에 안 써 있으면 사용자에게 묻거나, 기존 총액을 회차 수로 나눠
     회당 단가를 역산했다는 점을 반드시 각주(※)로 명시한다. 추측한 숫자를 마치 확정
     금액처럼 제시하지 않는다.

## 작업 순서

### 1. 반 목록(마스터 데이터) 확보

사용자가 대화 중에 반 목록을 주거나, 프로젝트에 기존 문서(예: `썸머_수업_회차_수강료.docx`,
`강의실_배정.docx` 같은 파일)가 있으면 그걸 기준으로 삼는다. 각 반마다 다음 정보가
필요하다:
- 학년/반명 (예: `[고2]_유신/창현A (미적1)`)
- 선생님
- 요일 패턴 (예: 화·목, 월(수)금, 토 — 괄호 표기는 "주 대체 요일"이라는 뜻으로, 별다른
  말이 없으면 **본 요일만** 쓰고 괄호 안 요일은 무시한다. 예: "화(목)"은 화요일만.
  "월(수)금"은 월+금만, 수는 무시. 실제로 어느 주에 대체 요일을 썼는지 원본 회차
  기록이 있으면 그걸 우선한다.)
- 과금 방식과 단가/정액 (회당 vs 1개월 정액)
- 과목/그룹 (수학/국어/영어/약술논술/과학 등 — 문서 섹션 구분용)

빠진 정보가 있으면 절대 만들어내지 말고 사용자에게 확인한다.

### 2. 기간 결정

- 기본: 달력월 전체
- 사용자가 범위·시작일·분리 요청("8월 따로 9월 따로")을 언급하면 그 지시를 그대로 반영
- 여러 반이 있고 반마다 기간이 다르면(예: "이 두 반만 9월로", "이 반은 8/15부터") 반별로
  따로 `gen_dates.py`를 호출한다 — 전체를 한 번에 뭉뚱그리지 않는다.

### 3. `gen_dates.py`로 날짜 계산

`scripts/gen_dates.py --help` 참고. 요약:

```bash
# 회당 수강료제, 기본 1개월
python3 scripts/gen_dates.py --month 2026-09 --weekdays tue,thu --fee 50000

# 회당 수강료제, 임의 기간
python3 scripts/gen_dates.py --start 2026-08-17 --end 2026-09-30 --weekdays sat --fee 62500

# 1개월 정액제 — fee 옵션을 주지 않는다 (곱하면 안 되므로), 날짜/회차만 받는다
python3 scripts/gen_dates.py --month 2026-09 --weekdays mon,wed,fri

# 한 반을 여러 구간으로 나눠 각각 계산 (예: 8월 따로 / 9월 따로)
python3 scripts/gen_dates.py --weekdays sat --split 2026-08-15:2026-08-31 \
    --split 2026-09-01:2026-09-30 --fee 80000
```

요일 코드: `mon/tue/wed/thu/fri/sat/sun` 또는 `월/화/수/목/금/토/일`. 한 반이 주 2회 이상
수업하면(예: 화·목) 콤마로 여러 요일을 한 번에 넣는다 — 한 번의 호출로 그 주의 모든
수업일을 얻는다.

정액제인데 기간이 정확히 1개월이 아닌 경우(예: "8/17~9/30"처럼 달 경계를 걸침): 정액
그대로 적용할 수 없으므로, 사용자가 별도 지시를 주지 않았다면 회차 수만 계산해 두고
"※ 정액제 - 기간이 1개월이 아니므로 금액 별도 확인 필요" 라고 각주를 달아 총액을 함부로
확정하지 않는다. 사용자가 "1개월 정액으로, 9월만 계산" 처럼 기간을 못박아 주면 그 지시를
따른다.

### 4. 결과 정리 및 문서 작성

출력은 과목(섹션) → 선생님(소제목) → 반(굵게, 요일/시간/단가 포함) → 날짜 줄(회차/금액)
순서로 정리한다. 예시 한 줄:

```
[고2]_유신/창현A (미적1) (신영준T) - 화(목) 18:00-22:00 / 토 9:00-13:00 [회당 62,500원]
- 9/1, 8, 15, 22, 29 (총 5강, 312,500원)
```

사용자가 워드 문서(.docx)로 달라고 하거나, 기존에 .docx로 주고받던 맥락이면 `docx` 스킬을
반드시 함께 사용해서 파일을 만든다 (docx-js로 새로 만들거나 기존 파일을 편집). 섹션은
`[ 수학 ]`, `[ 국어 ]`, `[ 영어 ]` 처럼 원본 문서 스타일을 따르고, 선생님 소제목은
`<선생님T>` 형식을 유지한다. 가정/추정이 들어간 항목은 문서 안에 눈에 띄는 방식(예:
빨간 이탤릭 각주)으로 표시해서 확정 전 확인이 필요함을 알린다.

문서가 아니라 채팅으로 짧게 물어본 질문(예: "이 반 9월에 몇 번이야?")이면 굳이 파일을
만들지 말고 대화창에 바로 답한다.

### 5. 이후 수정 요청 대응

사용자가 "이 반은 8월부터", "이건 삭제", "이 반은 요일을 바꿔서" 처럼 반별로 개별 수정을
요청하는 일이 매우 흔하다. 전체를 다시 만들지 말고, 해당 반만 다시 `gen_dates.py`로
재계산해서 문서의 그 부분만 갱신한다 (docx 편집 시 `str_replace` 등으로 해당 블록만 교체).

## 관련 파이프라인: 회차·수강료 / 강의실 배정 / HTML용 시간표

회차·수강료, 강의실 배정 문서, HTML용 시간표 엑셀, 요일×시간 격자 HTML 시간표(선생님별/
강의실별)는 서로 연결된 산출물이다. 보통은 회차·수강료를 먼저 확정하고 그걸 바탕으로
강의실을 배정한 뒤 HTML용 산출물을 만들지만, 상황에 따라 강의실 변경이나 HTML 시간표
수정 요청이 먼저 들어올 수도 있다 — 그때는 그 요청부터 바로 처리하고, 관련된 다른
산출물은 필요하면 나중에 같이 갱신한다.

### 데이터 모델: `data/classes.json`

모든 산출물의 단일 소스. 스키마는 `data/classes.schema_example.json` 참고. 핵심 구조:

```json
{
  "teachers": {"T01": "맥심", "T08": "신영준"},
  "classes": [
    {
      "id": "C005",
      "name": "[고2] 유신/창현 A (미적1)",
      "teacher_id": "T08",
      "subject": "수학",
      "grade": "고2",
      "pricing": {"type": "per_session", "unit_fee": 62500, "count": 12, "total": 750000},
      "sessions": [
        {"day": "화", "start": "18:00", "end": "22:00", "room": "6강의실"},
        {"day": "토", "start": "09:00", "end": "13:00", "room": "6강의실"},
        {"day": "목", "start": "18:00", "end": "22:00", "room": "1강의실", "clinic": true}
      ]
    }
  ]
}
```

- `pricing.type`: `per_session`(회당 단가×횟수) 또는 `flat_monthly`(정액, 절대 곱하지 않음).
- `sessions[].clinic: true`: **원문에서 요일이나 시간이 괄호로 표시된 것은 전부 클리닉이다.**
  예: "화(목)"의 (목), "월(수)금"의 (수), "(화)(목)=9강의실", "(클리닉)=5강의실",
  "정규(13:00-14:30)=9강의실 / 클리닉(14:30-15:30)=7강의실" 전부 클리닉을 뜻한다.
  괄호 없이 그냥 "화", "월·금"처럼 쓰인 요일은 정규다.
- `sessions[].room: "미정"`: 아직 강의실이 안 정해진 경우. 검증·시간표에서 자동 제외되고
  HTML 시간표에는 "미정"으로만 표시된다.
- `sessions[].group`: 여러 반이 같은 시간에 같은 방을 의도적으로 같이 쓰는 경우(합반,
  클리닉 연합반)에 공통 태그를 붙인다. 같은 group 태그를 가진 세션들은 클리닉이든
  정규든 상관없이 항상 하나로 합쳐진다.
  **주의: group은 실제로 시간이 겹칠 때만 단다.** 시간이 안 겹치고 그냥 순서대로
  이어지는 반들(예: A반 18-20시, B반 20-22시)은 같은 강의실을 써도 group을 달지 않는다
  — 안 겹치는 클리닉/합반 후보는 자동 겹침 감지가 알아서 따로 둔다. group을 잘못
  붙이면(실제로 안 겹치는데 강제로 합쳐버리면) 사용자에게 안 겹치는 두 반이 하나로
  보이는 오류가 생긴다(실제로 한 번 발생했던 실수). **`validate.py`를 돌리면 이런
  "불필요한 group 태그"도 같이 검사해서 알려주니, group을 새로 달거나 수정한 뒤에는
  항상 `validate.py`로 확인한다.**
- **클리닉끼리는 자동으로 합쳐진다** — `merge_utils.merge_sessions()`가 같은 강의실·
  같은 요일에서 시간이 겹치는 클리닉 세션들을 group 태그 없이도 자동으로 하나로 묶어서
  반명을 " / "로 나열한 항목을 만든다 (`build_room_view.py`, `build_html_xlsx.py` 둘 다
  적용됨). 정규(클리닉 아님) 세션끼리는 절대 자동으로 합치지 않는다 — 정규끼리 시간이
  겹치면 그건 실제 이중배정 오류일 수 있으므로 `validate.py`가 따로 잡아야 한다. 정규를
  합치고 싶으면 반드시 `group` 태그를 명시적으로 달아야 한다 (예: 엄형국T A/B 합반).

**새 학기·새 프로그램마다 이 파일을 처음부터 다시 만들 때**: 확정된 강의실 배정
문서(수업일정·수업시간·강의실이 반별로 정리된 텍스트/docx)를 반별로 읽으면서, 위 괄호
규칙에 따라 정규/클리닉 세션으로 나눠 `classes.json`을 채운다. 요일·시간·강의실 표기가
반마다 다른 문서 관용구를 쓰더라도(예: "정규(...)=" 라벨식, "(클리닉)=" 라벨식 등),
`classes.json`에 넣을 때는 전부 "괄호=클리닉" 하나의 규칙으로 통일해서 저장한다 —
표기가 원문마다 달라도 저장은 항상 같은 형태로.

```bash
# 1) 강의실 배정 문서 (docx) — 반명/요일-시간/강의실/수강료를 과목별로 정리
python3 scripts/build_room_doc.py

# 2) HTML용 시간표 엑셀 (반명 / 요일-시간 / 강의실, 정규·클리닉 각각 별도 행,
#    겹치는 클리닉은 자동으로 한 행에 합쳐짐)
python3 scripts/build_html_xlsx.py

# 3) 요일×시간 격자 HTML — 강의실별 (요일 탭 전환, 시간 비례 배치, 겹치는 클리닉은
#    자동으로 하나의 박스에 합쳐짐). 출력 파일명은 index.html (깃허브 페이지 등에
#    올릴 때 기본 랜딩 페이지가 되도록 이 이름을 씀 — 바꾸지 말 것)
python3 scripts/build_room_view.py

# 4) 요일×시간 격자 HTML — 선생님별 (행=선생님, 열=요일, 카드 스택, 강의실 링크, 주간 총 시간)
```

`validate.py`는 세 가지를 검사한다: (1) 물리적으로 불가능한 강의실 이중배정,
(2) group 태그가 붙어 있지만 실제로는 시간이 안 겹치는 세션(불필요한 group일 가능성),
(3) **합쳐진(합반/클리닉 합반) 박스 전체 미리보기** — 어떤 반들이 하나로 합쳐졌고
그 라벨이 "합반"인지 "클리닉 합반"인지 보여준다.

**파일을 사용자에게 전달하기 전에 (3)번 목록을 항상 눈으로 확인한다.** 요일에 괄호가
있는 반(클리닉)과 괄호 없는 반(정규)이 우연히 같은 그룹으로 묶여서 라벨이 잘못
매겨지는 경우가 실제로 있었다 (예: 정규끼리 합쳐졌는데 그중 하나에 클리닉 세션이
섞여 들어가 전체가 "클리닉"으로 잘못 표시됨). 이 목록에서 각 합반이 정규 세션들만
모였으면 "합반", 클리닉이 하나라도 섞였으면 "클리닉 합반"이 맞는지 반별 요일/시간
표기(괄호 유무)와 대조해서 확인한 뒤 전달한다.

`merge_utils.py`는 2)~5)가 공용으로 쓰는 자동 합치기 로직이다 (직접 실행하는 파일은
아님). 두 가지 함수가 있다:
- `merge_sessions()` — 강의실별 시간표(3번)에서 씀. 반과 반 사이(cross-class)의 합반·
  클리닉연합을 처리한다.
- `combine_class_sessions()` — 선생님별·학년별 시간표(4·5번)에서 씀. **한 반 자체의
  세션을 카드 하나로 정리**하는 규칙:
  - 강의실이 "미정"인 세션은 아예 제외한다 (강사·학년별 화면에는 강의실 배정이 끝난
    반만 보여준다 — 강의실 배정 전이면 아직 확정된 수업이 아니기 때문).
  - 같은 반이 같은 요일·같은 시간에 강의실을 2개 동시에 쓰면(예: 수요일 클리닉연합이
    8·9강의실을 같이 쓰는 경우) 카드 하나로 합치고 강의실을 "8·9강의실"처럼 표기한다.
    강의실별 시간표(3번, `merge_sessions`)는 이 규칙을 안 쓴다 — 거기는 강의실이
    기준축이라 각 방에 따로 나와야 한다.
  - 같은 반이 같은 강의실에서 정규 수업 끝나자마자 바로 클리닉으로 이어지면(예: 13시
    수업 시작, 16시 정규 끝, 바로 16-17시 클리닉) 카드 하나로 합쳐서 "정규+클리닉"
    라벨을 붙인다. 강의실이 다르면 안 합친다 (다른 방이면 사실상 다른 활동이므로).

모든 스크립트는 `data/classes.json`을 읽어서 `output/`에 결과를 쓴다.
**`classes.json`을 고친 뒤에는 필요한 스크립트를 다시 실행**해서 산출물이 서로 어긋나지
않게 한다. `validate.py`가 겹침을 보고하면, 실제 물리적 충돌인지(강의실 재배정 필요)
아니면 의도된 합반인지(`group` 태그 누락) 확인하고 고친 뒤 다시 돌린다.

### 학년별 시간표 (학부모 공개용)

학부모에게 보여줄 시간표는 전체 시간표가 아니라 **학년별로 따로** 만든다
(`build_grade_view.py <학년>`). 같은 학년·같은 과목에 여러 병행반(예: 이의/광교 연합반
vs 유신/창현반)이 있어서 시간이 겹쳐도, 요일×시간 격자가 아니라 **요일 컬럼 + 카드
스택** 방식이라 카드가 그냥 여러 장 쌓일 뿐 절대 겹치지 않는다. 페이지 맨 위에는 과목
필터 버튼(전체/국어/영어/수학/과학 등)을 두되, **처음 열었을 때는 항상 "전체"가
기본값**이라 버튼 존재를 몰라도 학년 전체 시간표가 바로 보인다. 필터 버튼 색은 시간표
안 과목별 카드 색과 맞춰서, 설명 없이도 버튼과 카드를 직관적으로 연결할 수 있게 한다.
모바일에서는 요일 컬럼이 세로로 쌓이고, 넓은 화면(760px 이상)에서는 7일이 가로로
나열되도록 반응형으로 만든다.

### 작업 순서

요청 내용에 따라 시작점이 다를 수 있다:
- 회차·수강료부터 바뀌는 경우: 이 스킬 앞부분 절차대로 회차·수강료를 확정한 뒤,
  `data/classes.json`에 반영하고 이어서 강의실 배정·HTML 산출물을 갱신한다.
- 강의실만 바뀌는 경우: `classes.json`의 해당 `sessions`만 고치고 바로 관련 스크립트를
  실행한다. 회차·수강료 문서를 다시 만들 필요는 없다.
- HTML 시간표·엑셀만 손보면 되는 경우: `classes.json`을 고치고 2)·3)·4)만 다시 실행한다.

공통 절차:
1. `data/classes.json`에서 해당 반의 `sessions`(또는 반 전체)를 수정/추가/삭제한다.
2. `validate.py`로 강의실 이중배정이 없는지 확인한다. 있으면 `group` 태그로 의도된
   합반을 구분하거나, 사용자에게 실제 방 배정을 다시 물어본다.
3. 영향받는 산출물을 다시 생성한다 (확실치 않으면 5개 스크립트 전부 재실행해도
   무방하다 — 실행이 빠르다).
4. 결과 파일들을 사용자에게 전달한다. 무엇을 바꿨는지 간단히 요약한다 — 사용자가 매번
   어디가 바뀌었는지 직접 대조하지 않아도 되게.

### 사용자가 "강의실 배정 파일이 바뀌었어, 이거 보고 다시 만들어줘" 라고 할 때

이 요청은 위의 "강의실만 바뀌는 경우"와 다르다 — 사용자가 정확히 뭐가 바뀌었는지
말해주지 않고, 문서(또는 노션 페이지 등) 전체를 다시 보라고 하는 상황이다. 이럴 때는:

1. **문서를 처음부터 끝까지 다시 읽는다.** 이전에 봤던 버전을 기억에 의존해 재사용하지
   않는다 — 파일이든 노션 페이지든 다시 fetch해서 전체를 읽는다. 노션처럼 여러 섹션이
   누적된 문서(예: 이번 학기 자료 아래에 지난 학기·프리썸머 자료가 그대로 남아있는
   경우)는 "지금 이 학기" 섹션만 골라서 보고, 오래된 섹션은 참고용으로만 취급한다.
2. **반 하나하나를 현재 `classes.json`과 대조한다.** 요일, 시간, 강의실, 신설/폐강
   여부를 전부 비교한다 — 일부만 훑어보고 "안 바뀐 것 같다"고 넘기지 않는다.
3. **문서 안에서 서로 모순되는 내용이 있으면 추측하지 않는다.** 같은 반이 다른 요일로
   두 번 적혀 있거나, 어떤 선생님 섹션이 통째로 빠져 있는 등 애매한 경우(실제로 있었던
   사례: 장현명T가 "수업일정" 섹션엔 있는데 "강의실 배정" 섹션엔 통째로 빠져 있어서
   실제로 폐강된 건지 확인이 필요했던 경우) 임의로 판단해서 반영하지 말고, 어떤 부분이
   애매한지 구체적으로 짚어서 사용자에게 물어본다.
4. 확인된 변경사항만 `classes.json`에 반영하고, `validate.py`로 검증한다 — 특히 반이
   새로 추가되거나 삭제되면 기존에 없던 충돌이 새로 생길 수 있으니 꼭 다시 돌려본다.
5. 영향받는 산출물을 재생성해서 전달하고, 무엇을 바꿨는지와 확인이 더 필요한 부분을
   같이 요약한다.
