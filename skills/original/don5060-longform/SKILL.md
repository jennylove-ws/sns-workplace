## [1] 소재 선정

`research/video_catalog.md`를 읽고 반응이 좋았던 Shorts를 고른다. 판단 기준은
CLAUDE.md의 "⭐ 진짜 관문: Viewed vs. Swiped Away"를 우선으로 하되, 지금은 YouTube API
조회가 사용자 결정으로 중단 중이므로 **조회수·반응은 사용자에게 직접 물어본다**(API 재개
전까지 `research_channel.py` 등으로 직접 조회하지 않는다).

좋은 롱폼 소재의 조건:
- 이미 짧은 버전에서 반응이 검증됨(같은 얘기를 처음부터 새로 도박하지 않는다)
- 본문에 **숫자·제도·비교·체크리스트로 확장할 거리**가 있는 소재가 정보그래픽 컴포넌트와
  잘 맞는다(예: "숨은 돈 찾기"처럼 실행 가능한 항목이 여러 개인 소재, "형제자매 재산 문제"처럼
  "이렇게 말하지 말고 이렇게" 대조가 되는 소재)
- 순수 감정선 사연 하나만으로는 그래픽 재료가 부족할 수 있다 — 그런 소재는 도입부(원본
  Shorts 사연, 실사/AI 이미지 위주)로 쓰고, 중반~후반에 같은 주제의 제도/통계/체크리스트를
  붙여 확장한다(정보그래픽 컴포넌트 위주)

## [2] 대본 확장

원본 Shorts 대본(50~60초)을 4~6분 분량으로 늘린다. 요약하는 게 아니라 반대 방향 —
**같은 사건을 더 깊이 파고, 관련 사실·통계·제도·체크리스트를 추가**한다.

- 구조: 도입(원본 훅 재구성 또는 확장) → 챕터 여러 개(사건 전개 + 관련 정보 확장) →
  결론(노후자산 프레임으로 수렴, 채널 공통 원칙). 챕터 = 오디오 파일 하나 단위(아래 [4] 참고)
- `전체대본.md`(전체 나레이션 원문)와 `TTS_분할.md`(챕터별로 나눠 TTS 생성용 — 이 분할이
  그대로 오디오 파일 1개=`N.wav` 단위가 되고, 나중에 씬 코드가 그 오디오 길이에 맞춰
  타이밍을 잡는다)를 함께 작성한다
- 대본에 **포토리얼 영상 클립을 텍스트 프롬프트로 생성하는 걸 전제하지 않는다** — Remotion도
  텍스트만으로 실사 영상을 만들어주진 못한다. 실사/AI 파트는 정지 이미지(켄번즈로 움직임을
  줌)이고, 움직이는 그래픽은 전부 코드로 그린다. 각 구간에 실사 이미지가 어울리는지, 아니면
  정보그래픽(숫자 스포트라이트, 표, 체크리스트, 대조 카드)이 어울리는지 구상하며 쓴다.
- 자막·나레이션 원칙은 Shorts와 같다: 숫자는 나레이션에 한글로 풀어 쓰고 자막은 숫자로,
  발음이 경음화되는 단어는 나레이션에만 소리 나는 대로 표기(`short-script-writer.md` 참고).
- **`기획_브리프.md`**를 함께 작성해 이 영상만의 팔레트·톤·비주얼 방향을 정한다. 팔레트는
  영상별로 다르다(시리즈 기본은 다크네이비/브론즈, "숨은 돈 찾기"는 골드 "발견" 팔레트로
  예외 적용된 적 있음) — 고정값을 가정하지 말고 이 문서에서 그때그때 정한다. `remotion_project`
  의 `src/constants.ts`에 이미 정의된 채널 기본 팔레트를 이 브리프가 override할 수 있다.

## [3] 비트 기획 (필수, 생략 불가)

**코드를 쓰기 전에 전체 대본을 비트(Sequence) 단위로 쪼개고 각 비트의 비주얼을 셋 중
하나로 미리 분류한다**(`donui-gwejeok-video` 스킬의 원칙 + `돈5060_롱폼`의 옛
`longform-video-design` 스킬의 3분류 원칙을 합친 것):

1. **재사용 컴포넌트 / 신규 인라인 정보그래픽** (목표 70~80%) — 숫자 스포트라이트, 표,
   체크리스트, 비교/대조 카드, 사이트 카드 등. 나레이션에 구체적 숫자·명사·대조 개념이 있으면
   여기 속한다.
2. **실사/AI 이미지 + 켄번즈** — 챕터당 **최소 1컷**은 넣는다(전혀 없으면 사용자가 지적한
   전례가 다른 채널에서 있었다). 같은 이미지의 재사용은 **영상 전체에서 최대 2회**로 제한한다.
3. **앰비언트 배경 장식**(파형/이퀄라이저 등) — 구체적으로 보여줄 게 없는 연결어·전환·수사적
   질문 구간에만, 같은 스타일을 연속으로 쓰지 않는다.

여기에 더해 **강조 문장 텍스트**(자막과 거의 동일한 큰 볼드 텍스트)는 영상 전체 하드캡
2~4개로 제한한다(챕터 전환점 등 정말 중요한 문장에만 예약).

자막 한 비트 = 의미 단위 하나, 나레이션 그대로(요약·의역 금지), 반드시 한 줄에 들어가게
쪼갠다(안 들어가면 줄바꿈이 아니라 비트를 더 쪼갠다). 계획을 말로 명시("총 N개 비트 —
정보그래픽 N개, 실사 N개, 앰비언트 N개, 강조 N개(상한 4)")한 뒤에만 코드를 쓰기 시작한다.
이 단계를 생략하면 "텍스트만 있는 슬라이드", "화면 콘텐츠와 자막이 같은 문장을 중복" 같은
과거 다른 프로젝트에서 실제로 반복됐던 실수가 재발하고, 렌더링까지 끝난 뒤에야 발견해
재작업 비용이 커진다.

## [4] 오디오

- TTS는 챕터(=오디오 파일 하나, `public/audio/<슬러그>/N.wav`) 단위로 생성한다. 각 파일을
  **연결/사용 전에 개별 검증**(전사 diff + `ffmpeg silencedetect`)한다 — 나중에 나쁜
  세그먼트를 찾는 게 훨씬 어렵다.
- `ffprobe`로 실측 길이를 재서 `timeline.json`(챕터별 startSec/durationSec, 총 길이)을
  만든다. **대본의 "예상 시간"은 추정치일 뿐, 실측 길이가 진실이다** — 코드가 이 실측값에
  맞춰 타이밍을 잡는다(반대가 아니다).
- **숫자 검증**: whisper류 전사가 핵심 통계(예: "404만원"을 "44만원"으로)를 잘못 알아들은
  전례가 있다. 전사가 대본과 자릿수·값이 의미 있게 다르면 어느 쪽도 조용히 믿지 말고
  **사용자에게 확인**을 요청한다. TTS가 실제로 오발음했을 수도 있다.
- 돈5060-유튜브팀의 `scripts/generate_tts.py`(faster-whisper 받아쓰기 로직 포함)를 챕터별
  생성에 재사용할 수 있는지 검토한다 — 이미 검증된 한국어 TTS 호출/발음 표기 규칙(경음화 등)을
  그대로 가져오는 게 새로 만드는 것보다 안전하다.

## [5] 실사 이미지 생성

**⚠ 구글 클라우드(Vertex AI) 호출은 한 번에 1건씩, 60초 간격 (2026-09-28 사용자 지시).** 롱폼 이미지를 연달아 만들다 분당 한도(429)에 걸린 뒤 정한 규칙이다. 이미지 1장 → 60초 → 다음 1장, 이미지와 TTS 사이도 60초. `generate_image.py`·`generate_tts.py`가 `scripts/vertex_throttle.py`로 자동 대기하니 **반드시 이 두 함수를 거쳐 호출**하고, Vertex를 직접 부르는 코드·병렬 실행(스레드, 여러 프로세스 동시)을 쓰지 않는다. 롱폼은 이미지가 많아 시간이 오래 걸리니(30장이면 30분 이상) 백그라운드로 돌리고 기다린다. 429가 나면 전역 재시도 정책(최대 3회) 안에서만 다시 실행한다.

돈5060-유튜브팀의 `scripts/generate_image.py`(Gemini/Imagen, 인물 일관성 레퍼런스 지원)를
그대로 재사용해 필요한 실사 이미지를 만든다. Shorts와 같은 규칙을 적용한다:
- 씬마다 장소·시간대·샷 크기를 구체적으로 지정(매번 같은 구도가 되지 않게, `video-producer.md`
  2번 항목 참고)
- 등장인물이 있으면 캐릭터 레퍼런스 포트레이트로 얼굴·의상 일관성 유지
- 이미지 재사용은 영상 전체 최대 2회([3]의 규칙)
- 만든 이미지는 `remotion_project/public/images/<슬러그>/`에 넣는다

## [6] Remotion 씬 작성

**`remotion` 스킬을 엔트리 포인트로 호출한다**(프레임 기반 사고, 미디어 임포트, 렌더 파이프라인
같은 리모션 범용 지식은 이 스킬에 있다). `remotion_project`는 **2026-09-28에 이미
스캐폴딩·설치 완료됐다**(`npx create-video@latest --yes --blank --no-tailwind`로 생성,
`npm install` 완료, `npx tsc --noEmit` 통과 확인). 새 세션에서 이 스킬을 쓸 때 폴더가 이미
있으면 이 단계를 다시 하지 않는다 — 아래는 처음 만들 때 실제로 밟은 절차 기록이다:

**스캐폴딩 절차(완료됨, 참고용)**:
1. `돈5060_롱폼\remotion_project`에서 `npx create-video@latest --yes --blank --no-tailwind
   remotion_project`(공식 Remotion 스타터, blank 템플릿)로 새 프로젝트를 만들었다.
2. `package.json`의 `name`을 `don5060-longform`처럼 이 프로젝트 것으로 정한다(아직 안 함 —
   기본값 그대로 남아있으면 첫 영상 작업 시 바꾼다).
3. `src/constants.ts`, `src/loadFonts.ts`를 새로 작성하되 **다른 리모션 프로젝트에서 실제로
   검증된 원칙**을 적용한다: `FPS=30, WIDTH=1920, HEIGHT=1080`, 채널 기본 팔레트(다크네이비/
   브론즈, 영상별 override는 [2]의 `기획_브리프.md`), 그리고 **Noto Sans KR을
   `public/fonts/`에 로컬 파일로 받아 `FontFace` API로 직접 로드**한다(`@remotion/google-fonts`
   의 CDN 방식은 렌더 환경에 따라 인증서 문제로 실패할 수 있다는 전례가 있으니 처음부터
   로컬 폰트로 간다).
4. `src/components/`를 이 영상들에 맞게 새로 설계한다. [3]의 3분류를 코드로 옮기되, **이름과
   구조만 참고하고 구현은 새로 짠다** — 컴포넌트 세트 예시:
   - 정보그래픽: 숫자 스포트라이트, 표, 체크리스트, 비교/대조 카드(빨강 ✕ vs 골드 ✓), 사이트
     카드, 인용 카드 — `돈5060_롱폼`의 옛 HyperFrames 4편에서 이미 디자인이 검증된 것들을
     Remotion 컴포넌트로 새로 구현한다.
   - 실사: `SlideImage`류(켄번즈 줌/팬)
   - 앰비언트: 파형/이퀄라이저류 — **텍스트 전용 비트에만**, 연속으로 같은 스타일 금지
   - 자막: 하단 자막 자동화 컴포넌트(챕터 전체 자막을 한 번만 렌더링해서 프레임 매칭 —
     씬 코드에서 개별 호출하지 않는다), 중앙 강조 텍스트(자막 복붙 금지, 키워드만)
   - 오디오: 챕터별 `<Audio>` 배치
   - 돈5060 소재에 맞는 비유가 필요하면(예: 유류분 비율을 저울로, 명의신탁을 자물쇠로)
     그때 그 영상 전용으로 새로 만든다 — 처음부터 범용 비유 라이브러리를 다 갖추지 않는다.
- `src/videos/<슬러그>/Composition.tsx` — 이 영상 전용 컴포지션. 챕터 오디오 길이를 이어
  붙여 전체 `durationInFrames`를 정하고, [3]의 비트 계획대로 `<Sequence>`를 배치한다.
- `src/Root.tsx`에 새 영상마다 `<Composition id="<슬러그>">`로 등록한다.

**막힐 때 참고할 곳(코드를 복사하는 게 아니라 "이렇게 짜면 되는구나"를 확인하는 용도)**:
`https://github.com/jennylove-ws/sns-workplace`(브랜치
`claude/remocion-image-audio-editing-7izo61`)에 "돈의 행방" 채널의 실제 구현이 있다 —
자막을 `slides`/`subtitleCues` 두 배열로 분리하는 구조, 이미지 재사용 최대 2회 같은 규칙이
실제 코드로 어떻게 들어갔는지 궁금하면 GitHub MCP로 열어본다.

**지켜야 할 기술 규칙(다른 리모션 프로젝트에서 실제로 겪은 문제들)**:
- `useCurrentFrame()`으로 현재 프레임에서 화면이 어때야 하는지 계산한다. `setTimeout`,
  `requestAnimationFrame`, CSS `transition`처럼 실제 경과 시간에 의존하는 방식은 프레임 단위
  캡처에서 작동하지 않거나 매 프레임 같은 상태로 캡처될 수 있다(`remotion` 스킬의
  "프레임 기반 사고" 참고).
- 랜덤해 보이는 모션(예: 이퀄라이저 바 흔들림)에 `Math.random()`을 쓰지 않는다 — 프레임마다
  다시 계산되어 렌더가 끊기거나 일관성이 깨진다. 고정된 의사-랜덤 시퀀스를 미리 계산해 쓴다.
- 이미 정보그래픽이 핵심 텍스트를 화면에 보여주고 있다면, 같은 문장을 하단 자막에 또는 중앙
  강조 텍스트로 중복해서 넣지 않는다(둘이 같은 화면 영역을 두고 경쟁하게 된다).
- 부모 컨테이너 자체에 기본 `opacity:0`이 걸려 있으면 자식 fade-in과 별개로 부모도 명시적
  fade-in 트윈이 필요하다(안 그러면 자식이 아무리 움직여도 안 보인다).

## [7] 타입체크 → 스틸컷 검수 → 구간 렌더

1. `npx tsc --noEmit` — 에러 0개 확인.
2. `npx remotion still src/index.ts <슬러그> out/frame.png --frame=<확인할 프레임>` —
   비트 경계 프레임 몇 장을 정지 이미지로 뽑아 레이아웃 깨짐·텍스트 겹침·색상 대비를 렌더
   전에 육안 확인한다.
3. `npx remotion render src/index.ts <슬러그> out/<슬러그>.mp4` — 이 노트북은 램이 ~7.7GB로
   부족해 렌더가 느리거나 실패할 수 있다. 돈5060-유튜브팀 CLAUDE.md에 이미 정해진 대로
   **무거운 렌더링은 웹 Claude Code에서 수행**하고, 로컬은 대본·오디오·이미지 준비까지만
   담당하는 분업도 가능하다. 새 챕터 하나만 작업했다면 `--frames=<시작>-<끝>`으로 그 구간만
   렌더해서 전체를 다시 렌더하지 않는다.
4. 파일이 크면(채팅 전달 제한 등) ffmpeg로 압축한다(`-c:v libx264 -crf 26 -preset medium`
   에서 시작, 필요하면 28~30까지 올린다).

## [8] 완성 확인 (사람 검수 필수)

영상 파일을 사용자에게 전달하고 직접 재생 확인을 요청한다. 특히:
- 자막이 화면 콘텐츠와 겹치거나 중복되지 않는지
- 오디오가 챕터 경계에서 잘리지 않았는지
- 강조된 핵심 숫자가 대본과 일치하는지(TTS 오발음 가능성)
- 실사 이미지가 최소 1컷/챕터 들어갔는지, 같은 이미지가 3번 이상 반복되지 않는지

## [9] 썸네일 + 메타데이터

**롱폼은 Shorts와 달리 썸네일이 실제로 노출된다**(검색·홈 피드·채널 페이지). 현재 롱폼
CTR이 3.8%로 매우 낮으므로, `thumbnail-copywriter.md`의 원래 규칙(숫자형+경고/손실
프레이밍+대상 특정, 어두운 오버레이+굵은 고딕+3~5줄 컬러 텍스트)을 Shorts보다 **공들여서**
적용한다. 메타데이터는 `seo-metadata.md` 형식을 따르되, 검색형 트랙에 가까우므로 설명란·
태그 비중을 높인다.

**메타데이터 파일 맨 끝에 `[출처]` 칸을 둔다.** 근거가 **있는 것만** 적는다: 원본 Shorts와 그 소재 번호(`research/topic_pool.md`의 T-번호), `대본/*_출처.md`, 대본 속 법률·판례·통계·뉴스 문장의 실제 근거(기사 링크·판례 번호·기관 자료). 근거가 없으면 지어내지 말고 적지 않는다. 대본에 근거 없는 문장을 쓰는 것 자체는 괜찮다(각색 이야기). 롱폼은 제도 설명 비중이 커서 시청자가 사실 여부를 댓글로 자주 물으니, 답할 때 이 칸을 먼저 본다.

## [10] 업로드 + Shorts↔롱폼 연결

- 업로드는 항상 **비공개**로, 공개 전환은 매번 별도 확인(Shorts와 동일 원칙). 현재
  YouTube API 업로드·조회가 사용자 결정으로 중단 중이므로, 재개 전까지는 사용자가 Studio에서
  직접 올린다.
- **Shorts→롱폼 연결**(CLAUDE.md "다음에 기획할 것"의 미해결 지렛대): 원본 Shorts의 고정
  댓글이나 설명란에 이 롱폼 링크를 추가하고, 롱폼 설명란에도 원본 Shorts를 언급해 서로
  연결한다. 관련 동영상 연결(수동)도 안내한다.
- 완료 후 `research/video_catalog.md`에 롱폼 항목도 한 줄 추가해 기록을 남긴다(어떤 Shorts를
  심화한 것인지 명시).
