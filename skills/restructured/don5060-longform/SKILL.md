# 돈5060 롱폼 제작 워크플로우 (Remotion)

터진 Shorts 하나를 4~6분 가로(16:9) 롱폼으로 심화한다. 기술 스택은 **Remotion(React/TypeScript)** — 실사/AI 정지 이미지(켄번즈)와 코드 모션그래픽을 한 컴포지션에서 섞는다.

## ⚠ 놓치기 쉬운 규칙 (작업 내내)
1. **코드를 쓰기 전에 비트 기획 필수** — `longform-video-design` 체크리스트를 그대로 적용하고, 집계를 말로 밝힌 뒤에만 코드를 쓴다([3]).
2. **구글 클라우드(Vertex AI) 이미지·TTS는 한 번에 1건, 60초 간격** — `generate_image()`/`generate_tts()`만 거쳐 호출, 병렬 금지([5], `google-cloud-generation-limits`).
3. **실사 이미지 챕터당 최소 1컷, 같은 이미지 영상 전체 최대 2회.** 강조(큰 글씨) 문장 전체 2~4개.
4. **자막 = 내레이션 그대로, 한 비트 한 줄.** 의역·요약 금지, 넘치면 비트를 쪼갠다.
5. **오디오 실측 길이가 진실** — 대본 예상 시간이 아니라 `ffprobe` 실측으로 타이밍을 잡는다([4]).
6. **숫자 전사가 대본과 다르면 조용히 믿지 말고 사용자에게 확인**(예: "404만원"→"44만원" 오청 전례).
7. **돈의 행방(sns-workplace 저장소) 코드를 복사하지 않는다** — 원칙만 참고([6], 결정 배경).
8. **업로드는 항상 비공개**, 공개 전환은 매번 확인. 지금은 YouTube API 중단 중 → 사용자가 Studio에서 직접.
9. **각 단계 결과를 보여주고 확인받는다** — 완전 무인 자동 생성이 아니다(돈5060-유튜브팀 CLAUDE.md의 "인증되지 않은 콘텐츠" 정책·사람 검수 원칙이 롱폼에도 적용). 중간에 방향이 바뀌면 그 지점부터 다시 진행한다.

## [1] 소재 선정
- `research/video_catalog.md`에서 반응 좋았던 Shorts를 고른다. 기준은 CLAUDE.md의 "⭐ 진짜 관문: Viewed vs. Swiped Away" 우선.
- **YouTube API 조회는 사용자 결정으로 중단 중** → 조회수·반응은 사용자에게 직접 묻는다(재개 전까지 `research_channel.py` 등으로 조회하지 않는다).
- 좋은 소재:
  - 짧은 버전에서 반응이 이미 검증됨(처음부터 새로 도박하지 않는다)
  - **숫자·제도·비교·체크리스트로 확장할 거리**가 있음 — 정보그래픽과 잘 맞는다(예: "숨은 돈 찾기"처럼 실행 항목이 여러 개, "형제자매 재산 문제"처럼 "이렇게 말고 이렇게" 대조)
  - 순수 감정선 사연 하나뿐이면 그래픽 재료가 부족할 수 있다 → 도입부(원본 사연, 실사 위주)로 쓰고 중후반에 같은 주제의 제도/통계/체크리스트를 붙인다(정보그래픽 위주)

## [2] 대본 확장
원본 Shorts(50~60초)를 4~6분으로 늘린다. 요약의 반대 — **같은 사건을 더 깊이 파고 관련 사실·통계·제도·체크리스트를 추가**한다.
- 구조: 도입(원본 훅 재구성/확장) → 챕터 여러 개(사건 전개 + 정보 확장) → 결론(노후자산 프레임으로 수렴, 채널 공통 원칙). **챕터 = 오디오 파일 하나 단위.**
- `전체대본.md`(전체 내레이션)와 `TTS_분할.md`(챕터별 — 이 분할이 그대로 `N.wav` 단위가 되고 씬 코드가 그 길이에 맞춰 타이밍을 잡는다)를 같이 쓴다.
- **포토리얼 영상 클립 생성을 전제하지 않는다** — Remotion도 텍스트로 실사 영상을 못 만든다. 실사 파트는 정지 이미지(켄번즈), 움직이는 그래픽은 전부 코드. 구간마다 실사가 어울리는지 정보그래픽(숫자 스포트라이트, 표, 체크리스트, 대조 카드)이 어울리는지 구상하며 쓴다.
- 자막·내레이션 원칙은 Shorts와 같다: **숫자는 내레이션엔 한글로 풀어 쓰고 자막엔 숫자로**, 경음화되는 단어는 내레이션에만 소리 나는 대로(`short-script-writer.md`).
- `기획_브리프.md`로 이 영상만의 팔레트·톤·비주얼 방향을 정한다. **팔레트는 영상마다 다르다**(시리즈 기본 다크네이비/브론즈, "숨은 돈 찾기"는 골드 "발견" 팔레트로 예외) — 고정값을 가정하지 않는다. 브리프가 `remotion_project/src/constants.ts`의 채널 기본 팔레트를 override할 수 있다.

## [3] 비트 기획 (필수, 생략 불가)
**`longform-video-design` 스킬의 체크리스트를 그대로 따른다**(0번 계획 → 1번 자막 규칙 → 2번 버킷 → 3번 렌더 전 감사). 요점:
- 전체 대본을 비트(`<Sequence>`) 단위로 쪼개고 비트마다 분류: **정보그래픽(재사용 컴포넌트/신규 인라인, 목표 70~80%)** / **실사·AI 이미지+켄번즈(챕터당 최소 1컷, 같은 이미지 최대 2회)** / **앰비언트(구체적으로 보여줄 게 없는 연결어·전환·수사적 질문에만, 같은 스타일 연속 금지)** / **강조 문장(하드캡 2~4개, 챕터 전환점 등 정말 중요한 문장에만)**.
- 자막 한 비트 = 의미 단위 하나, 내레이션 그대로, 한 줄(안 들어가면 줄바꿈이 아니라 비트를 쪼갠다).
- 코드 전에 말로 명시: "총 N개 비트 — 정보그래픽 N개, 실사 N개, 앰비언트 N개, 강조 N개(상한 4)".
- 생략하면 "텍스트만 있는 슬라이드", "화면 콘텐츠와 자막이 같은 문장 중복" 같은 과거 실수가 재발하고, 렌더 뒤에야 발견해 재작업 비용이 커진다.

## [4] 오디오
- TTS는 **챕터 단위**(`public/audio/<슬러그>/N.wav`)로 생성하고, **연결/사용 전에 파일마다 검증**(전사 diff + `ffmpeg silencedetect`) — 나중에 나쁜 세그먼트를 찾는 게 훨씬 어렵다.
- `ffprobe`로 실측 길이를 재서 `timeline.json`(챕터별 startSec/durationSec, 총 길이)을 만든다. **대본의 예상 시간은 추정치, 실측이 진실** — 코드가 실측에 맞춘다(반대 아님).
- **숫자 검증**: whisper류 전사가 핵심 통계를 잘못 알아들은 전례("404만원"→"44만원"). 전사와 대본의 자릿수·값이 의미 있게 다르면 어느 쪽도 조용히 믿지 말고 **사용자에게 확인** — TTS가 실제로 오발음했을 수도 있다.
- 돈5060-유튜브팀 `scripts/generate_tts.py`(faster-whisper 받아쓰기 포함)를 챕터별 생성에 재사용할 수 있는지 검토한다 — 검증된 한국어 TTS 호출/발음 표기 규칙(경음화 등)을 가져오는 게 새로 만드는 것보다 안전하다.

## [5] 실사 이미지 생성
- **⚠ Vertex AI 호출은 한 번에 1건, 60초 간격**(2026-09-28 사용자 지시 — 롱폼 이미지를 연달아 만들다 분당 한도 429에 걸린 뒤 정함). 이미지 1장 → 60초 → 다음 1장, 이미지↔TTS 사이도 60초. `generate_image.py`·`generate_tts.py`가 `scripts/vertex_throttle.py`로 자동 대기하니 **반드시 이 두 함수를 거친다.** Vertex 직접 호출 코드·병렬 실행(스레드, 여러 프로세스) 금지. 이미지가 많아 오래 걸리니(30장이면 30분 이상) 백그라운드로 돌리고 기다린다. 429가 나면 전역 재시도 정책(최대 3회) 안에서만 다시 실행. 상세: `google-cloud-generation-limits`.
- 돈5060-유튜브팀 `scripts/generate_image.py`(Gemini/Imagen, 인물 일관성 레퍼런스)를 그대로 재사용. Shorts와 같은 규칙:
  - 씬마다 장소·시간대·샷 크기를 구체적으로(매번 같은 구도 금지, `video-producer.md` 2번 항목)
  - 등장인물이 있으면 캐릭터 레퍼런스 포트레이트로 얼굴·의상 일관성 유지
  - 재사용은 영상 전체 최대 2회
  - 결과는 `remotion_project/public/images/<슬러그>/`

## [6] Remotion 씬 작성
**`remotion` 스킬을 엔트리 포인트로 호출한다**(프레임 기반 사고, 미디어 임포트, 렌더 파이프라인 등 범용 지식).

프로젝트 기본 설정(처음 만들 때 적용한 원칙 — 없으면 이대로 만든다):
- `src/constants.ts`: `FPS=30, WIDTH=1920, HEIGHT=1080`, 채널 기본 팔레트(다크네이비/브론즈, 영상별 override는 `기획_브리프.md`)
- `src/loadFonts.ts`: **Noto Sans KR을 `public/fonts/`에 로컬 파일로 두고 `FontFace` API로 직접 로드** — `@remotion/google-fonts`의 CDN 방식은 렌더 환경에 따라 인증서 문제로 실패한 전례가 있다.

컴포넌트(`src/components/`) — [3]의 분류를 코드로. **이름과 구조만 참고하고 구현은 새로 짠다**:
- 정보그래픽: 숫자 스포트라이트, 표, 체크리스트, 비교/대조 카드(빨강 ✕ vs 골드 ✓), 사이트 카드, 인용 카드 — 옛 HyperFrames 4편에서 디자인이 검증된 것들을 새로 구현
- 실사: `SlideImage`류(켄번즈 줌/팬)
- 앰비언트: 파형/이퀄라이저류 — **텍스트 전용 비트에만**, 같은 스타일 연속 금지
- 자막: 하단 자막 자동화 컴포넌트(챕터 전체 자막을 한 번만 렌더링해 프레임 매칭 — 씬 코드에서 개별 호출하지 않는다), 중앙 강조 텍스트(자막 복붙 금지, 키워드만)
- 오디오: 챕터별 `<Audio>` 배치
- 돈5060 소재에 맞는 비유(유류분 비율=저울, 명의신탁=자물쇠 등)는 필요할 때 그 영상 전용으로 만든다 — 범용 비유 라이브러리를 미리 다 갖추지 않는다.

영상별:
- `src/videos/<슬러그>/Composition.tsx` — 챕터 오디오 길이를 이어 붙여 전체 `durationInFrames`를 정하고, [3]의 비트 계획대로 `<Sequence>` 배치.
- `src/Root.tsx`에 영상마다 `<Composition id="<슬러그>">` 등록.

기술 규칙(다른 리모션 프로젝트에서 실제로 겪은 문제):
- `useCurrentFrame()`으로 현재 프레임의 화면을 계산한다. `setTimeout`, `requestAnimationFrame`, CSS `transition`처럼 실제 경과 시간 기반은 프레임 캡처에서 안 움직이거나 같은 상태로 찍힌다.
- 랜덤해 보이는 모션(이퀄라이저 흔들림 등)에 `Math.random()` 금지 — 프레임마다 다시 계산돼 끊기거나 일관성이 깨진다. 고정 의사-랜덤 시퀀스를 미리 계산해 쓴다.
- 정보그래픽이 이미 핵심 텍스트를 보여주면 같은 문장을 하단 자막·중앙 강조 텍스트에 중복하지 않는다(같은 화면 영역을 두고 경쟁).
- 부모 컨테이너에 기본 `opacity:0`이 걸려 있으면 자식 fade-in과 별개로 부모도 명시적 fade-in이 필요하다(안 그러면 자식이 안 보인다).

막힐 때: `https://github.com/jennylove-ws/sns-workplace` 브랜치 `claude/remocion-image-audio-editing-7izo61`(`main`엔 README만)에 "돈의 행방" 채널 실제 구현이 있다 — 자막 `slides`/`subtitleCues` 두 배열 분리, 이미지 재사용 최대 2회가 코드로 어떻게 들어갔는지 GitHub MCP(`mcp__*__get_file_contents` 등)로 **열어보기만** 한다(2026-09-28 접근 확인).

## [7] 타입체크 → 스틸컷 검수 → 구간 렌더
1. `npx tsc --noEmit` — 에러 0개.
2. `npx remotion still src/index.ts <슬러그> out/frame.png --frame=<프레임>` — 비트 경계 프레임 몇 장으로 레이아웃 깨짐·텍스트 겹침·색 대비를 렌더 전에 확인.
3. 렌더 직전 `longform-video-design` 3번 자체 감사(버킷별 개수 명시).
4. `npx remotion render src/index.ts <슬러그> out/<슬러그>.mp4` — 노트북 램 ~7.7GB로 부족해 느리거나 실패할 수 있다. 돈5060-유튜브팀 CLAUDE.md대로 **무거운 렌더는 웹 Claude Code**에서, 로컬은 대본·오디오·이미지 준비까지만 하는 분업도 가능. 챕터 하나만 작업했으면 `--frames=<시작>-<끝>`으로 그 구간만.
5. 파일이 크면 ffmpeg 압축: `-c:v libx264 -crf 26 -preset medium`에서 시작, 필요하면 28~30.

## [8] 완성 확인 (사람 검수 필수)
영상을 전달하고 직접 재생 확인을 요청한다. 특히:
- 자막이 화면 콘텐츠와 겹치거나 중복되지 않는지
- 오디오가 챕터 경계에서 잘리지 않았는지
- 강조된 핵심 숫자가 대본과 일치하는지(TTS 오발음 가능성)
- 실사가 챕터당 1컷 이상, 같은 이미지 3회 이상 반복 없음

## [9] 썸네일 + 메타데이터
- **롱폼은 썸네일이 실제로 노출된다**(검색·홈 피드·채널 페이지). 현재 롱폼 CTR 3.8%로 매우 낮음 → `thumbnail-copywriter.md` 규칙(숫자형+경고/손실 프레이밍+대상 특정, 어두운 오버레이+굵은 고딕+3~5줄 컬러 텍스트)을 Shorts보다 **공들여** 적용.
- 메타데이터는 `seo-metadata.md` 형식, 검색형 트랙이라 설명란·태그 비중을 높인다.
- **메타데이터 파일 맨 끝에 `[출처]` 칸** — 근거가 **있는 것만**: 원본 Shorts와 소재 번호(`research/topic_pool.md`의 T-번호), `대본/*_출처.md`, 대본 속 법률·판례·통계·뉴스 문장의 실제 근거(기사 링크·판례 번호·기관 자료). 없으면 지어내지 않고 적지 않는다. 대본에 근거 없는 문장 자체는 괜찮다(각색). 롱폼은 제도 설명이 많아 댓글로 사실 여부를 자주 물으니 답할 때 이 칸을 먼저 본다(블로그도 이 칸을 근거로 쓴다).

## [10] 업로드 + Shorts↔롱폼 연결
- 항상 **비공개** 업로드, 공개 전환은 매번 확인. YouTube API 업로드·조회는 사용자 결정으로 중단 중 → 재개 전까지 사용자가 Studio에서 직접.
- **Shorts→롱폼 연결**(CLAUDE.md "다음에 기획할 것"의 미해결 지렛대): 원본 Shorts 고정 댓글이나 설명란에 롱폼 링크, 롱폼 설명란에도 원본 Shorts 언급. 관련 동영상 연결(수동)도 안내.
- 완료 후 `research/video_catalog.md`에 롱폼 항목 한 줄(어떤 Shorts를 심화했는지 명시).
- 이후 블로그·클립 배포는 `sns-upload`.

## 결정 배경 (왜 이렇게 하나 — 다시 뒤집지 않도록)
- **HyperFrames → Remotion 전환(2026-09-28 사용자 결정)**: 검증된 옛 롱폼 4편(퇴직후_건강보험료 v1/v2, 숨은돈찾기, 형제자매와재산문제)은 HyperFrames(HTML/CSS/SVG/GSAP + headless Chrome)였다. 실사/AI 이미지와 코드 모션그래픽을 한 컴포지션에서 자연스럽게 섞기 위해, 같은 시니어 타깃 채널 "돈의 행방"(구 "돈의 궤적")이 1화(25파트)를 실제 렌더링까지 검증한 Remotion 방식으로 옮겼다.
- **"포크"가 아니다(2026-09-28 사용자 지적으로 정정)**: `remotion`은 사용법을 담은 **지식 스킬**이라 포크할 코드가 없다. `sns-workplace` 저장소는 실제 코드지만 **돈의 행방 전용**(패키지명 `donui-gwejeok`, 그 채널 팔레트·자판기/시소/톱니 비유 컴포넌트가 박혀 있음). 그래서 돈5060은 **공식 스타터로 새 프로젝트를 만들었고**, 저 저장소에서는 원칙(자막 `slides`/`subtitleCues` 분리, 로컬 `FontFace` 폰트 로드, `Math.random()` 금지)만 빌려온다. 코드 파일이나 그 채널 전용 컴포넌트는 복사하지 않는다.
- `longform-video-design`은 2026-09-28 `돈5060_롱폼` 프로젝트 한정 스킬에서 전역 스킬로 옮겼다(다른 창·웹 Claude에서도 보이게).
